# RSI 设计与版本演进

ComfyFlash 的执行路径由三个层次组成。Agent 在任务层根据 Tone 契约安排素材和参数，通过观察包决定是否调整。Engine 在执行策略层按明确的 GPU 准入、显存模式和交付规则运行，并将结果转成结构化证据。`RSI/` 在改进机制层保存提案、对照、版本和决定，供 Agent 在明确发起评审时读取。

| 层次 | v0.2 P0/P1 能力 | 后续可验证目标 |
| --- | --- | --- |
| 任务 | 动态发现 Tone，通过 Artifact 和尾帧衔接步骤。 | 对同一 Plan 比较局部重跑、参数修订及用户约束保持率。 |
| 执行策略 | 记录 GPU、模型、工作负载、阶段耗时、内存、失败与媒体有效性。 | 对照验证设备准入、模型亲和性、错峰加载和 OOM 恢复。 |
| 改进机制 | 手工登记问题、两套策略、测试集、指标、结论及回滚依据。 | 以留出的项目样本衡量提出假说、挑选试验和判断采纳的方法。 |

## 对照与采纳规则

改进提案先指定 `baseline_policy_version`、`candidate_policy_version` 和 `rollback_to`，再描述可证伪的假说。对照尽量固定输入、seed、模型、精度、LoRA、分辨率、采样器、时长和驱动。记录当时的空闲 RAM/显存、串并发、冷/热启动条件，并留出代表性的真实样本。至少同时检查成功率、尾延迟、吞吐、显存和 RAM、交付技术有效性、用户约束保持率。审美或表演质量由独立评审记录来源与局限。遇到 OOM 样本应保留失败阶段和资源上下文。一次成功或一次失败只能说明该次运行条件。

采纳需要有复现可能的对照证据、明确的回滚版本以及人工决议。SQLite API 会拒绝缺少对照记录或回滚版本的采纳。撤销时保留原决议和证据并记录回滚依据。v0.2 P0/P1 的版本与决议只用于追溯。实际运行仍取现有配置和内置策略。接入候选评估与采纳由后续阶段验证。

Agent 可以按需读摘要及原始 JSONL，重建某类请求的历史，并回看其 Artifact。证据不足时把经验标为未知。这轮的日志和人工版本目录是后续可验证改进的基础，自动试验、画像学习和改进机制迭代列入 P2/P3。存储字段与维护命令见 [RSI 存储说明](CF_V02_RSI_STORAGE.md)。
